# F1 — Research API & Multi-Surface Interface Boundary

Status: **READY**  
Priority: **P0**

## Purpose

Make the already-earned quantitative capabilities straightforward to consume from ordinary Python without going through Qt/QML, while preserving the production quantitative core as the single source of financial semantics.

F1 is primarily an API-curation and interface-boundary milestone. It must not reimplement pricing, Greeks, hedging, market normalization, implied-volatility inversion, Heston pricing/calibration, validation, or performance logic.

## Central question

Can a quant researcher use the platform's major workflows directly from Python through a coherent, documented, Qt-free surface that can also support notebooks, exports, and a browser analytics client?

## Dependencies

Required MERGED repository capabilities:

- M1–M9;
- UI1–UI5;
- the current frontend-neutral qf_platform.application layer;
- the current quantitative core and committed evidence artifacts.

Historical version/release publication is **not** a dependency.

## Parallelization

F1 is the shared-contract milestone for the F-series and should run alone by default.

F2, F3, and F4 remain BLOCKED until F1 is repository-defined MERGED.

## Required orientation

In addition to the global repository orientation, inspect:

- src/qf_platform/application/**;
- public package surfaces in pricing, sensitivity, control, inference, market-data, and validation;
- presentation adapters that already express frontend-neutral evidence;
- the native Workbench architecture and its dependency-direction tests;
- current examples/scripts and package metadata.

## Scope

1. Audit the existing public/programmatic surface before introducing a new façade.
2. Identify the smallest coherent Python-facing entry points for:
   - Black-Scholes / independent valuation;
   - Greeks / sensitivity;
   - dynamic Delta hedging;
   - market evidence and implied volatility;
   - Heston forward valuation;
   - Heston calibration / identifiability;
   - Black-Scholes vs Heston validation/model-risk evidence;
   - committed performance evidence where useful to researchers.
3. Curate or add public imports/documented constructors/helpers only where they materially reduce coupling to internal module layout.
4. Preserve mathematically meaningful typed inputs and immutable result/evidence objects.
5. Add runnable plain-Python examples that exercise the major workflows without desktop imports.
6. Add durable architecture documentation for the multi-surface boundary once the implemented seams are known.
7. Add regression/architecture tests that prove the research-facing surface remains Qt-independent.

A dedicated qf_platform.research package is allowed only if the audit shows it earns a clear responsibility. Do not create it merely for naming symmetry. Re-exporting selected existing application/domain contracts may be sufficient.

## Non-goals

- no new quantitative model or numerical method;
- no universal Problem/Method/Result runtime hierarchy;
- no generic workflow engine or plugin registry;
- no REST service;
- no Dash UI;
- no notebooks;
- no Excel/report generation;
- no desktop redesign;
- no semantic-version or release work.

## Architecture constraints

Required direction:

~~~text
quantitative core / immutable evidence
            ↑
frontend-neutral application/research semantics
            ↑
 Python scripts / notebooks / exports / Dash / Qt
~~~

Protect:

~~~text
research convenience API != new quantitative authority
frontend adapter != financial calculation
Qt controller != reusable research API
presentation value != source quantitative result
~~~

No public research helper may require PySide6.

Avoid one giant run-everything API. Keep concrete workflows explicit enough that model, problem, method, numerical configuration, and evidence remain inspectable.

## Deliverables

- curated/documented Python research-facing surface;
- runnable plain-Python examples for the earned workflow families;
- tests for public imports and representative executions;
- Qt-free dependency-boundary test for the research surface;
- architecture documentation explaining how Python, notebooks, exports, Dash, and Qt should consume shared semantics without duplicating finance logic;
- any necessary documentation updates to public API navigation.

## Validation

At minimum:

- canonical ./scripts/check_all;
- focused public-API/import tests;
- representative deterministic executions for each exposed workflow;
- architecture/dependency checks proving no PySide6 dependency;
- numerical results must match the already-authoritative production methods/evidence rather than introducing parallel calculations.

## Acceptance criteria

- [ ] A clean Python consumer can run representative pricing, sensitivity, hedging, market/IV, Heston, calibration, and validation workflows without importing desktop code.
- [ ] Public examples use supported, documented imports rather than private module paths.
- [ ] New convenience seams, if any, are concrete and consumer-earned.
- [ ] No quantitative formulas or model semantics are duplicated in the interface layer.
- [ ] Existing Qt Workbench behavior remains downstream of the same authoritative application/core semantics.
- [ ] F2, F3, and F4 can consume the merged F1 surface without depending on each other's implementation.
