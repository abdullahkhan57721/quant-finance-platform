# F2 — Reproducible Jupyter Research Studies

Status: **REVIEW**  
Priority: **P1**

Work unit: Issue #57 / PR #58 / branch `f2-57-jupyter-studies`

## Purpose

Add a small set of high-quality, reproducible notebooks that demonstrate how a quant researcher investigates the platform's models and evidence using the merged F1 Python-facing API.

The notebooks are research/presentation consumers, not an alternate implementation location.

## Central question

Can a reviewer or researcher understand and reproduce the project's core numerical/model-risk story from notebooks that call production APIs rather than hiding finance logic in cells?

## Dependencies

- F1 — Research API & Multi-Surface Interface Boundary (MERGED).

## Parallelization

After F1 merges, F2 may run in parallel with F3 and F4 if live file/dependency overlap is low.

F2 must not consume unmerged F3/F4 code.

## Required orientation

Inspect:

- the merged F1 public/research API and examples;
- M1–M8 model/evidence documentation;
- committed evidence artifacts and deterministic fixtures;
- current dependency/CI policy for optional development/research tooling.

## Scope

Create exactly three flagship research studies unless repository evidence justifies a smaller equivalent structure:

1. **Pricing, numerical methods, and Greeks**
   - European option setup;
   - Black-Scholes analytic valuation;
   - CRR and Monte Carlo comparison;
   - convergence/error evidence;
   - analytic vs finite-difference Greeks.

2. **Dynamic Delta hedging and model-risk pressure**
   - explicit hedge assumptions;
   - rebalance-frequency experiment;
   - volatility misspecification;
   - proportional transaction costs;
   - replication-error analysis.

3. **Observed SPX evidence, Heston calibration, and held-out validation**
   - observed/normalized data distinction;
   - implied-volatility/skew context;
   - Black-Scholes benchmark fit;
   - Heston calibration and identifiability diagnostics;
   - predeclared training/evaluation split;
   - contract-level residuals and held-out comparison;
   - explicit limitations/non-claims.

Use committed fixtures/derived evidence for the default repository execution path. Do not require live market-data access.

## Non-goals

- no production formulas or algorithms implemented in notebooks;
- no notebook-only business rules;
- no new model calibration/validation method;
- no broad tutorial library;
- no live data dependency;
- no Dash/Qt duplication;
- no release/version milestone.

## Architecture constraints

~~~text
notebook
   ↓
merged F1 public/research API
   ↓
application + quantitative core
~~~

Notebooks may transform results into tables/plots for explanation, but quantitative authority remains in production code.

If helper code becomes substantial or reused, move it into an appropriate tested Python module instead of duplicating cells.

## Deliverables

- three clearly named notebooks under a durable notebooks/ structure;
- optional research dependency group only for tools actually needed to execute/render them;
- automated execution/smoke verification in a clean environment;
- README/index describing what each notebook demonstrates and its assumptions;
- stable plotting/table output suitable for technical review;
- explicit links to repository model documentation for important formulas and evidence.

## Validation

- every notebook executes top-to-bottom from a clean checkout with its declared optional dependencies;
- default execution is deterministic where the underlying method permits it;
- no network access is needed;
- representative values agree with production/committed evidence within documented tolerances;
- canonical repository quality checks continue to pass;
- notebook metadata/output handling avoids volatile-noise churn.

## Acceptance criteria

- [ ] A reviewer can run all three studies without the desktop UI.
- [ ] The notebooks consume supported F1 interfaces only.
- [ ] Important quantitative results are visible as tables/plots and remain traceable to typed production results/evidence.
- [ ] The flagship validation notebook preserves the bounded M7 interpretation rather than overstating temporal forecasting, identification, trading profitability, or hedge superiority.
- [ ] CI or a repository-native check catches notebooks that no longer execute.
