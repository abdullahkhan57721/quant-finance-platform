# F4 — Dash/Plotly Internal Analytics Workbench

Status: **ACTIVE**  
Priority: **P1**

Work unit: Issue #61 / branch `f4-61-dash-analytics`

## Purpose

Add a thin browser-based analytics client that resembles an internal finance research/risk application while consuming the same authoritative quantitative/application semantics as Python and the native Qt Workbench.

## Central question

Can the platform expose its major research workflows through a focused Dash/Plotly application without creating a second quantitative implementation or rebuilding every desktop feature?

## Dependencies

- F1 — Research API & Multi-Surface Interface Boundary (MERGED).

F3 exports are deliberately not a dependency so F3 and F4 may run concurrently. Download/export integration may be deferred to F5 if needed.

## Parallelization

After F1 merges, F4 may run in parallel with F2 and F3 if live contract/file overlap is safe.

## Required orientation

Inspect:

- merged F1 research-facing API;
- existing frontend-neutral application and presentation modules;
- Qt Workbench only as a behavior/UX reference, not an implementation dependency;
- M2–M8 evidence structures;
- packaging and CI conventions.

## Scope

Build a deliberately thin internal-analytics web client with documented local launch.

Target workspaces:

1. **Overview**
   - platform problem families;
   - flagship empirical/model-risk evidence;
   - links/navigation to concrete workflows.

2. **Valuation & Greeks**
   - contract/financial inputs;
   - Black-Scholes analytic, CRR, and Monte Carlo comparison;
   - convergence/uncertainty;
   - Greeks.

3. **Dynamic Hedging**
   - assumptions/configuration;
   - rebalance-frequency evidence;
   - misspecification/transaction-cost views;
   - replication error.

4. **Market / Implied Volatility**
   - observed-market evidence;
   - implied-volatility/skew views;
   - provenance/normalization context.

5. **Heston Pricing & Calibration**
   - forward valuation comparison;
   - calibration results;
   - residuals;
   - multi-start/conditioning/identifiability evidence.

6. **Model Validation**
   - training vs held-out metrics;
   - contract-level residuals/errors;
   - Heston stability/conditioning;
   - explicit non-claims;
   - M8 performance evidence when useful.

The application may expose fewer navigation pages if several related workflows are coherently combined; the quantitative capabilities above must remain reachable.

## Non-goals

- no React/TypeScript;
- no REST service requirement;
- no cloud deployment requirement;
- no user authentication/multi-tenancy;
- no live market feed;
- no persistence/workspace database;
- no recreation of every Qt feature;
- no finance calculations in Dash callbacks;
- no semantic-version/release work.

## Architecture constraints

Required direction:

~~~text
Dash / Plotly
      ↓
web-specific presentation/adapters
      ↓
merged F1 application/research semantics
      ↓
quantitative core / committed evidence
~~~

Dash must not import the Qt desktop layer.

Callback code should normalize interaction state and call tested application/research functions. Pricing formulas, Greeks, calibration residuals, validation metrics, and financial conventions do not belong in callbacks.

Renderer-specific Plotly objects remain downstream of renderer-neutral/typed data where practical.

## Deliverables

- optional web dependency group;
- browser application package/module;
- documented local launch command;
- the concrete workspaces above;
- Plotly figures/tables built from authoritative results/evidence;
- loading/error/empty states appropriate to expensive computations;
- focused tests for web adapters/callback service functions and application construction;
- smoke proof that the local app starts without Qt;
- architecture/docs updates for the web client boundary.

## Validation

- canonical core quality gate plus any web-specific type/lint/test gate;
- local/headless startup smoke;
- representative callback/service tests;
- key displayed numbers trace to F1/application/core outputs;
- no network dependency for default examples;
- no PySide6 import in the web client dependency chain.

Full browser-driver end-to-end tests are optional unless implementation risk justifies them.

## Acceptance criteria

- [ ] A user can launch a local browser analytics workbench from documented commands.
- [ ] Major existing workflow families are inspectable without the desktop application.
- [ ] The web app consumes the merged F1 surface and does not duplicate quantitative logic.
- [ ] The M7 held-out/model-risk interpretation and M8 measured-performance caveats remain intact.
- [ ] The native Qt Workbench and web app coexist as sibling clients of shared semantics.
