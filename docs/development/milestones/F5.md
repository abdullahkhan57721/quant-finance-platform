# F5 — Multi-Surface Integration & Portfolio Documentation

Status: **ACTIVE**  
Priority: **P1**

Work unit: Issue #63 / branch `f5-63-multisurface-integration`

## Purpose

Integrate and harden the Python, notebook, export, Dash, and Qt surfaces into one coherent quantitative platform story without turning this milestone into a release/version exercise.

## Central question

Can a reviewer or teammate understand which interface to use, run each supported surface, and trust that all surfaces are downstream of the same quantitative semantics and evidence?

## Dependencies

All must be repository-defined MERGED:

- F2 — Reproducible Jupyter Research Studies;
- F3 — Analyst Interoperability & Structured Exports;
- F4 — Dash/Plotly Internal Analytics Workbench.

F1 is inherited through those dependencies.

## Parallelization

F5 is an integration milestone and should not begin before F2/F3/F4 merge and their final public contracts are known.

Independent maintenance may run separately if it does not conflict.

## Required orientation

Inspect:

- F1 public/research API;
- all F2 notebooks;
- F3 export adapters/examples;
- F4 web client;
- native Qt Workbench;
- README and architecture docs;
- current CI/workflow coverage for core, desktop, notebooks/research, reporting, and web surfaces.

## Scope

1. Make the repository present one coherent multi-surface architecture:
   - Python API for programmatic research;
   - Jupyter for reproducible investigation;
   - structured XLSX/CSV/JSON exports for analyst/reporting workflows;
   - Dash/Plotly for internal browser analytics;
   - PySide6/QML for the native desktop Workbench.
2. Update reviewer-facing documentation so the first screen explains:
   - what the platform is;
   - quantitative problems it solves;
   - strongest empirical/model-risk result;
   - available interfaces;
   - exactly how to run each interface.
3. Add/refresh an architecture diagram showing sibling clients over shared quantitative/application semantics.
4. Add cross-surface consistency checks around a small set of canonical scenarios where practical.
5. Ensure optional dependency groups remain separable; users should not need Qt to use Python/Dash/notebooks, or Dash to use Qt.
6. Add clear navigation from README/docs to notebooks, web workbench, desktop workbench, exports, evidence, and core API examples.
7. Reconcile duplicate presentation logic discovered during integration only when a stable shared responsibility is demonstrated.
8. Harden error messages/launch instructions and clean-install smoke paths for the newly added surfaces.

## Non-goals

- no semantic-version bump requirement;
- no GitHub Release/tag publication;
- no installer/notarization project;
- no React frontend;
- no REST service;
- no Excel add-in;
- no new financial model;
- no C++ work without new profiling evidence;
- no universal UI framework across Dash and Qt.

## Architecture constraints

Target story:

~~~text
                         quantitative core
                               ↑
                    application/research semantics
                               ↑
        ┌──────────────┬───────┼────────┬──────────────┐
        │              │       │        │              │
     Python         Jupyter   exports   Dash          Qt/QML
   programmatic     research  XLSX/CSV  analytics     desktop
                               /JSON
~~~

Sibling clients may share frontend-neutral data/presentation responsibilities that have actually converged, but they must not be forced into a universal UI abstraction.
